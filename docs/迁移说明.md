# 从直连 OpenAI / Anthropic 迁移到 TokenRouter

已有项目不需要重写。TokenRouter 在协议面上保持 OpenAI Chat、OpenAI Responses（无状态子集）与 Anthropic Messages 的官方形态，客户端只改 **`base_url`** 与 **`api_key`** 两个值，SDK、请求体、响应体解析都不动。

需要先理解一个边界：**设备负责鉴权、选路、转发、计量与管理，不跑模型**。请求路径是“客户端 → 设备 → 管理员配置的上游”，模型算力仍在上游服务，设备不改变请求要去的模型能力。兼容接口也不等于全部模型与多模态都覆盖，可用模型以 `GET /v1/models` 和「使用API」页为准。

## 一、两处改动总表

| 改动项 | 直连时 | 改成 TokenRouter |
| --- | --- | --- |
| OpenAI 风格 `base_url` | `https://api.openai.com/v1` | `http://<设备地址>/v1`（**必须含 `/v1`**） |
| Anthropic `base_url` | `https://api.anthropic.com` | `http://<设备地址>`（**用根地址，不要加 `/v1`**） |
| `api_key` | `sk-...` / `sk-ant-...` / 上游厂商 Key | 设备「我的API密钥」新建的 `sktr_...` |
| 模型名 | 官方模型名 | 用 `GET /v1/models` 返回的 `id`，原样复制 |

`<设备地址>` 是设备根地址：内网 IP（如 `http://192.168.1.20`）或设备域名（形如 `https://<名称>.tokenrouter.host`）。填写地址本身时不带路径，再按上面的规则决定是否补 `/v1`。

## 二、OpenAI SDK：只补 `/v1`

OpenAI 协议面由设备在 `/v1` 下提供，SDK 的 `base_url` 要含 `/v1`，SDK 自己再拼 `/chat/completions` 或 `/responses`。

### Python

```python
from openai import OpenAI

# 之前：直连官方
# client = OpenAI(api_key="sk-...")

# 现在：指向设备，base_url 含 /v1，api_key 换成 sktr_
client = OpenAI(
    base_url="http://<设备地址>/v1",
    api_key="sktr_...",
)
```

### Node.js

```js
import OpenAI from "openai";

const client = new OpenAI({
  baseURL: "http://<设备地址>/v1", // 注意属性名是 baseURL
  apiKey: "sktr_...",
});
```

### 走环境变量时

```diff
- OPENAI_BASE_URL=https://api.openai.com/v1
- OPENAI_API_KEY=sk-...
+ OPENAI_BASE_URL=http://<设备地址>/v1
+ OPENAI_API_KEY=sktr_...
```

OpenAI 官方 SDK 会读这两个环境变量；如果项目里是显式传参，按上面的代码改。

## 三、Anthropic SDK：用根地址，别加 `/v1`

Anthropic SDK 会在 `base_url` 后面自己拼 `/v1/messages`，所以这里传设备根地址。手工加 `/v1` 会得到 `/v1/v1/messages`。

### Python

```python
from anthropic import Anthropic

# 之前：直连官方
# client = Anthropic(api_key="sk-ant-...")

# 现在：base_url 用设备根地址，不要加 /v1
client = Anthropic(
    base_url="http://<设备地址>",
    api_key="sktr_...",
)
```

### Node.js

```js
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic({
  baseURL: "http://<设备地址>", // 不要写成 http://<设备地址>/v1
  apiKey: "sktr_...",
});
```

### 走环境变量时

```diff
- ANTHROPIC_BASE_URL=https://api.anthropic.com
- ANTHROPIC_API_KEY=sk-ant-...
+ ANTHROPIC_BASE_URL=http://<设备地址>
+ ANTHROPIC_API_KEY=sktr_...
```

Anthropic Messages 同时接受 `Authorization: Bearer sktr_...` 与 `x-api-key: sktr_...`；用官方 SDK 时不用手写请求头，SDK 会按自己的约定发送。

## 四、迁移后的验证顺序

1. 列模型，确认密钥与地址都通：

   ```bash
   bash scripts/list_models.sh
   ```

   返回 `200` 和模型 `id` 列表即通过；列表只包含当前密钥属主可用的文本模型。

2. 用 curl 发一次请求，排除 SDK 层干扰：

   ```bash
   export TR_BASE_URL="http://<设备地址>"
   export TR_API_KEY="sktr_..."
   curl -sS "$TR_BASE_URL/v1/chat/completions" \
     -H "Authorization: Bearer $TR_API_KEY" \
     -H "Content-Type: application/json" \
     -d '{"model":"<上一步的模型 id>","messages":[{"role":"user","content":"你好"}]}'
   ```

3. 跑仓库里的最小示例，看回复与用量字段：

   ```bash
   python python/openai_chat.py
   python python/anthropic_messages.py
   node node/chat.mjs
   ```

4. 最后再跑业务代码。业务侧只应看到“地址变了、Key 变了”，不应出现请求体改写。

## 五、常见报错排查

### 401 未通过鉴权

按顺序检查：

- `TR_API_KEY` / `api_key` 是否为空，或复制时带进了空格、换行、引号；
- 用的 Key 是不是设备上的 `sktr_` 密钥。晨羽云的 `sk-...` 和上游厂商的 Key 都不能用于设备入口；
- 密钥是否已被删除或停用。删除后客户端会立即 401；
- 请求头是否为 `Authorization: Bearer sktr_...`（`Bearer` 后有空格）；用 SDK 时不要自己再拼一层。

401 表示“没通过鉴权”，不是额度或频率问题；额度或频率到顶是 429。

### 404 未找到

404 在设备侧有几类常见原因：

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| OpenAI SDK / curl 返回 404，提示路径不对 | `base_url` 少了 `/v1` | 改成 `http://<设备地址>/v1`。设备不会静默改写路径，会返回带修正提示的 404 |
| Anthropic SDK 返回 404 | `base_url` 多写了 `/v1`，请求变成 `/v1/v1/messages` | 改成设备根地址 `http://<设备地址>` |
| 路径本身写错 | 如 `/v1/chat/completion`、`/v1/message` | 核对为 `/v1/chat/completions`、`/v1/messages` |
| 模型名不对 | 模型不存在，或当前密钥无权使用该模型 | 设备对“模型不存在”和“无权使用”统一返回 404，避免泄露模型目录；用 `GET /v1/models` 返回的 `id` 原样复制 |

### 429 请求过多或额度到顶

响应会带 `Retry-After`。检查该密钥的 RPM 与日 / 周 / 月预算，以及密钥属主用户的预算；任一层到顶都会拒绝新的消费请求。查询模型列表、查询 / 取消任务不受预算拦截。

### 400 请求不合法

常见于缺少 `model`、模型不支持当前协议面，或请求体不符合官方 SDK 形态。先用仓库示例跑通，再把业务请求逐项加回去定位。

### 连不上或证书报错

- 确认设备地址、端口和网络可达；内网 IP 直连即可，不依赖厂商云；
- 设备域名（`https://<名称>.tokenrouter.host`）的证书由设备自己持有。如果是自签证书，把设备证书加入系统或运行时的信任链，不要用关闭证书校验的方式绕过。

## 六、事实边界

- 设备负责**鉴权、选路、转发、计量与管理**，**不跑模型**；模型算力在被配置的上游。
- 当前支持 **OpenAI Chat**（`POST /v1/chat/completions`）、**OpenAI Responses**（`POST /v1/responses`，无状态子集）、**Anthropic Messages**（`POST /v1/messages`）。
- **兼容接口不等于全部模型与多模态都覆盖。** 可用模型取决于设备配置与密钥属主权限，以 `GET /v1/models` 和「使用API」页为准；本仓库示例只覆盖文本对话。
- 请求路径是“客户端 → 设备 → 管理员配置的上游”，提示词与素材仍会发往该上游服务；除非上游本身就是局域网内自建服务。
- 设备地址变化后，只需更新 `base_url`；密钥属主可在「我的API密钥」重新复制明文。

## 七、回滚

把 `base_url` 与 `api_key` 改回原值即可，业务代码无需其他改动。
